## 本機驗收歷史與乾淨發布歷史

早期本機驗收快照 `fd45578` 含環境背景的文件，保留供本機重現；固定 ZIP 不變。後續匿名文件可在原本機歷史作增量提交，但舊祖先不適合直接傳輸。初次私人發布使用另一個無父 root 的 `publication` 分支，只納入經審查的原始碼、測試、設定模板、playbook 及匿名文件，推往遠端 `main`。後續公開沿用此分離的發布歷史，不接回私人本機祖先。

這是新增本機分支與新儲存庫的初始歷史，不刪除或改寫任何舊提交，也不重寫他人的遠端歷史。新 clone 的 `main` 不一定能解析 `fd45578`；以實際發布 commit 為開發基準，依來源對照 manifest 確認程式內容對應。歷史測試紀錄與新執行結果分開記錄。

只推送已批准的具體 ref，不使用 `--all`、`--mirror` 或全部 tags。從保留舊歷史的工作區操作時，先核對當前分支與遠端目的地；不得因忽略規則有效就認為所有可達歷史都適合上傳。

## 發布前逐檔與全歷史檢查

1. 核對 owner、repo、目前可見性、目標可見性與最新使用者授權；不得由建立 repo 或過往 private 授權推定可公開。本次公開目標已明確指定，仍須先完成內容與 metadata 審查。
2. 列出**待推分支全部可達提交、tree 與 blob**，審查內容及 metadata。既有 Git 作者設定維持不變，不捏造作者；若公開身份仍需另行決定，先暫停公開發布。
3. 只 stage 明確檔案清單。禁止 `data/`、`logs/`、`reports/`、資料庫、原始告警、私人檔案、秘密、local config、登入資訊與原始 sessions。`.gitignore` 不能清除過往提交。
4. 掃描憑證／私鑰樣式與真實使用者路徑，再人工區分合成 fixture、範例與實際證據；自動掃描不是沒有秘密的保證。合成測試不得包含真實告警 ID、私人內容或原始報告。
5. 核對 source／tests／config／playbook 與固定測試來源的雜湊，記錄文件差異。驗證 Markdown 連結、JSON 範例、CLI 名稱及限制一致。
6. 推送指定 feature 分支，透過 PR 更新預設分支，不直接推送 main。核對 PR head、合併結果與遠端 HEAD。內容確認後才變更可見性，再用受信任 API 回讀 PUBLIC 與 MIT 授權辨識結果；失敗或結果不明先查證，不盲目重推或改 force。

公開還會曝光既有 Git 作者 metadata 及 GitHub 端的 Actions／附件／PR 等歷史。需另外檢查這些公開面；原始碼掃描不能取代 metadata 檢查。作者 email 若不是 GitHub noreply，且無法確認已公開，先釐清公開身分範圍，不自行改寫歷史或假造作者。

新功能透過清楚範圍的分支與 PR review：說明觸發條件、前後行為、資料／權限影響、測試及未驗證範圍。敏感處置、外部傳輸、持續模型回合、額度或費用改變須另有具體批准；現有儲存庫存取不是永久授權。
